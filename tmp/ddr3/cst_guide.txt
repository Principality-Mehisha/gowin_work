1  About This Guide 
1.1 Purpose 
This manual describes the interface and use of FloorPlanner and the 
syntax definition of physical constraint for Arora Ⅴ FPGA products in order 
to help you add physical constraints to your design. As the software is 
subject to change without notice, some information may not remain 
relevant and may need to be adjusted according to the software that is in 
use. 
All physical constraints have higher priority than the global Place & 
Route settings in Gowin Software. The global Place & Route settings can 
be configured via clicking "Project > Configuration > Place & Route" from 
the menu bar in Gowin Software.

2  Physical Constraints Syntax 
Definition 
2.1 I/O Location Constraints 
The IO constraints can be used to constrain ports to the specified IO 
locations. The specific IO locations can be found in the device's Pinout 
manuals. 
Syntax 
IO_LOC "obj_name" obj_location [exclusive]; 
Syntax Rules 
 Each constraint statement must end with an English semicolon ";". 
 The constraint object obj_name must be enclosed in English double 
quotation marks. 
 In a constraint statement, multiple constraint locations (obj_location) 
can be specified, separated by English commas. For example, multiple 
IO locations can be written as "A11,B2". 
 Each part of the constraint statement must be separated by a space. 
Constraint Elements 
 obj_name 
obj_name is the name of the port in the example. 
 obj_location 
obj_location is the IO location, such as "A11", "B12", etc. If multiple 
locations are specified, they need to be separated by commas, such as 
"A11, B2". 
2 Physical Constraints Syntax Definition  2.2 I/O Attribute Constraints 
 
SUG1018-1.7E 5(77) 
 
 exclusive 
exclusive is optional and follows the constraint location, indicating that 
only the object specified by obj_name can be placed in the obj_location of 
the constraint statement.  
Examples 
Example 1 
IO_LOC "port0" G2; 
// The object port0 is constrained to the location G2 in the GW5AT-
15B-MBGA132 package. 
Example 2 
IO_LOC "port1" P10,N10,G2; 
// The object port1 is constrained to locations P10, N10, and G2 in the 
GW5AT-15B-MBGA132 package. During placement, the first valid location 
among the three will be used. 
Example 3 
IO_LOC "port2" P10,N10,G2 exclusive; 
// The object port2 is constrained to P10, N10, and G2 in the GW5AT-
15B-MBGA132 package, and these three locations can only be used by 
port2. 
2.2 I/O Attribute Constraints 
You can set attribute values for I/O, such as IO_TYPE, PULL_MODE 
and DRIVE, etc. For detailed attribute settings, please refer to the product 
datasheets. 
Syntax 
IO_PORT " obj_name " attribute = attribute_value; 
Note！ 
 Multiple attributes can be specified in a single constraint statement, with each 
attribute separated by a space. 
 For syntax rules, you can see Syntax Rules in Section 2.1. 
Constraint Elements 
 obj_name 
obj_name is the name of the port in the example.

 attribute 
Name of the IO attribute 
 attribute value 
The value of the IO attribute 
For the details of IO attribute and attribute value, you can see UG304, 
Arora Ⅴ Programmable IO (GPIO) User Guide. 
Examples 
Example 1 
IO_PORT "port_1" IO_TYPE = LVTTL33; 
// Sets port_1 IO_TYPE to "LVTTL33".

// Sets port_2 IO_TYPE to the LVTTL33; PULL_MODE value is set to

2.3 Primitive Location Constraints 
Primitive Constraints are used to constrain the primitives to the 
specified locations. 
LUT/DFF/DL/MUX/IOLOGIC/BSRAM/SSRAM/DSP/DDRDLL/PLL/DQS/MI
PI_DPHY_RX/ 
DSPLite/SCRAMBLE instances can be constrained using Primitive 
Constraints. 
Syntax 
INS_LOC "obj_name" obj_location [exclusive]; 
Note! 
For syntax rules, you can see Syntax Rules in Section 2.1. 
Constraint Elements 
 obj_name  
The constrained object, which refers to the instance name of the 
primitive. 
 exclusive 
The keyword "exclusive" is optional. It indicates that the obj_location 
2 Physical Constraints Syntax Definition  2.3 Primitive Location Constraints 
 
SUG1018-1.7E 7(77) 
 
specified in this constraint statement can only be used for placing the 
object defined by obj_name. 
 obj_location 
The valid location(s) for the primitive specified by obj_name. 
obj_location includes the following categories: 
1. LUT Constraint Location 
 A signal location specifying to LUT, such as, RxCy[0-3][A-B]. 
 A range of the locations specifying multiple rows or columns. 
- Includes multiple CLSs or LUTs: "RxCm", "RxCm[0-3]"   
- Specifies multiple rows: "R[x:y]Cm", "R[x:y]Cm[0-3]", 
"R[x:y]Cm[0-3][A-B]" 
- Specifies multiple columns: "RxC[m:n]", "RxC[m:n][0-3]", 
"RxC[m:n][0-3][A-B]" 
- Specifies multiple rows and columns: "R[x:y]C[m:n]", 
"R[x:y]C[m:n][0-3]", "R[x:y]C[m:n][0-3][A-B]" 
Note! 
 x, y in the LUT location refers to the row information of the GRID. 
 m, n in the LUT location refers to the column information of the GRID. 
 R in the LUT location represents the row, and C represents the column of the 
GRID. 
 0-3 in the LUT represents the index of the CLS within a GRID. 
 A-B in the LUT location represents the index of LUT location within a CLS. 
 For MUX, DFF, and DL primitives, the constraint locations are the same as 
those for LUTs. 
2. PLL Constraint Location 
The format for PLL constraint locations is either PLL_L or PLL_R, 
representing the left or right side of the device. If multiple PLLs are 
available on one side, they can be indexed as:  
PLL_L[0], PLL_L[1], ... 
PLL_R[0], PLL_R[1], ... 
3. BSRAM Constraint Location 
The writing format for BSRAM constraint location is "BSRAM_R10[0]" 
(the first BSRAM at row 10), "BSRAM_R10[1]"…. 
4. DSP Constraints Location

SUG1018-1.7E 8(77) 
 
The format for DSP constraint locations is DSP_R37[0] (the first DSP 
block in row 37), DSP_R37[1], ... 
If it is constrained to a macro, the format can be written as 
DSP_R37[0][A] or DSP_R37[0][B].   
Note! 
Each DSP block contains two macros. A macro refers to the location for one MULT18X18 
primitive. 
5. DDRDLL Constraint Location 
The writing format for DDRDLL constraint location is "DDRDLLM_TL", 
"DDRDLLM_TR". 
6. MIPI_DPHY_RX Constraint Location 
The writing format for MIPI_DPHY_RX constraint location is 
"QUAD[0]", "QUAD [1]". 
Note! 
MIPI_DPHY_RX constraints support the following devices: GW5A(S)(T)-138, but do not 
support exclusive. 
7. DSPLite Constraint Location 
The writing format for DSPLite constraint location is "R19C26", 
"R19C37"…,"R19C47". 
Note! 
DSPLite constraints support the following devices: GW5A(N)(R)T-15. 
8. SCRAMBLE Constraint Location 
The writing format for SCRAMBLE constraint location is "SCRM[0]", 
"SCRM[1]"… 
Note! 
SCRAMBLE constraints support the following devices: GW5A(N)(R)T-15, but the 
exclusive option is not supported. 
9. IOLOGIC Constraint Location 
IOLOGIC constraint locations refer to specific IO positions. Please 
refer to the Pinout manuals of the target device for detailed IO location 
information.  
Examples 
Example 1

2.4 Group Constraints 
The group constraints include Primitive Group Constraints and 
Relative Group Constraints. 
2.4.1 Primitive Group Constraints 
Primitive Group Constraint is used to define a group constraint. A 
group is a collection of various instance objects. The instances such as 
LUT, DFF, DL, IOLOGIC, Buffer, BSRAM, SSRAM, DSP, PLL, DDRDLL, 
DQS, DSPLite, or Buffer, IOLOGIC can be added to a group using the 
Primitive Group constraints. And the location constraints of all objects in 
the group can be achieved by constraining the location of the group. At the 
same time, Primitive Group constraints support the use of wildcard 
characters "?" and "*", where "?" matches a single character and "*" 
matches zero or more characters. 
Syntax 
Primitive Group Constraint Definition: 
GROUP group_name = { "obj_names" } [exclusive]; 
2 Physical Constraints Syntax Definition  2.4 Group Constraints 
 
SUG1018-1.7E 11(77) 
 
GRP_LOC group_name group_location[exclusive]; 
Note! 
 For syntax rules, you can see Syntax Rules in Section 2.1. 
 The primitive group constraint syntax supports the use of wildcards: "?" matches a 
single character, and "*" matches zero or more characters. 
 The primitive group constraint syntax consists of two statements: group definition 
and group location. If either is missing, the constraint is considered invalid.  
Constraint Elements 
 group_name 
Defines the name of a Primitive Group. 
 obj_name 
obj_name refers to the instance object added to the Primitive Group. 
 group_location 
Specifies the constraint locations for the group, such as 
group_location can be an IO, CFU, DQS, BSRAM, DSP, PLL, DDRDLL, or 
DSPLite location. 
 exclusive 
The keyword "exclusive" is optional, which is placed at the end of the 
group definition or the group location constraints. 
An object can be included in multiple groups, but the object can only 
be included in the group that the "exclusive" is added. 
The "exclusive" indicates that the constraints location can only be 
used by the objects in the group. 
Examples 
Example 1 
GROUP group_1 = { "lut1" "lut2" "lut3" "ins_4" };   
GRP_LOC group_1 R[3:4]C4 exclusive;   
// Creates a group named group_1, adding the objects lut1, lut2, lut3, 
and ins_4 to this group. All instances in the group are allowed to be placed 
within the region R[3:4]C4, and this region is exclusively reserved for 
instances in group_1. 
Example 2 
GROUP group_2 = { "lut_*" } exclusive;   
2 Physical Constraints Syntax Definition  2.4 Group Constraints 
 
SUG1018-1.7E 12(77) 
 
GRP_LOC group_2 R[2:3]C[2:4];   
// This example demonstrates the use of the wildcard *. A group 
named group_2 is created, which includes all instances whose names 
start with lut_, and all instances are exclusively assigned to this group. The 
instances can be placed within the region R[2:3]C[2:4]. 
2.4.2 Relative Group Constraints 
The instances such as LUT1~LUT4, DFF, DL, MUX2 relative location 
constraints can be realized using the Relative Group Constraints. 
Syntax 
Relative Group Constraint Definition: 
REL_GROUP group_name = { "obj_names" }; 
INS_RLOC “obj_name” relative_location; 
Note! 
 For syntax rules, you can see Syntax  in Section 2.1. 
 The relative group constraint syntax consists of two statements: group definition and 
group location. If either is missing, the constraint is considered invalid. 
Constraint Elements 
 obj_name 
Defines the name of a Relative Group. 
 relative_location 
Describes the relative location information of each constrained object 
within the group. 
Example 
REL_GROUP grp_1 = { "ins_1" "ins_2" "ins_3"}; 
INS_RLOC "ins_1" R1C1; 
INS_RLOC "ins_2" R2C3; 
INS_RLOC "ins_3" R0C5;

2.5 Resource Reservation Constraints 
The specified location or range can be reserved using the Resource 
Reservation constraints. 
Syntax 
LOC_RESERVE location [ -res_obj ]; 
Note! 
For syntax rules, you can see Syntax Rules in Section 2.1. 
Constraint Elements 
 location 
Reserved location information. Only locations of the following types 
can be reserved: CFU, IO, BSRAM, DSP, DDRDLL, PLL, DQS, 
MIPI_DPHY_RX, DSPLite, and SCRAMBLE. 
 res_obj 
It is optional, and it is only valid for CFU type in location. It supports 
two values: LUT and REG. Setting it to LUT means reserving only the LUT 
resources in the specified location, while setting it to REG meaning 
reserving only the REG resources. 
Examples 
Example 1 
LOC_RESERVE R2C3[0]-LUT; 
// The LUT resources in the first CLS of R2C3 are reserved. 
Example 2 
LOC_RESERVE R2C3[0]-REG; 
// The REG resources in the first CLS of R2C3 are reserved. 
Example 3 
LOC_RESERVE IOR3, IOR6, R2C3, R3C4; 
// The resources at locations IOR3, IOR6, R2C3, and R3C4 are 
reserved and cannot be used during the placement.

improve the efficiency of writing physical constraint files.

constraint files, and the output of constraint files

user design files

 Supports grid mode, macro cell mode and primitive mode of chip array 
 Supports Package View 
 Can display Chip Array and Package View synchronously 
 Supports real-time and differential display of constraint locations 
 Can generate locations by dragging 
 Supports I/O port attribute configuration and batch configuration 
 Supports display and editing functions of Clock Net Constraints 
 Supports constraints legality check 
 Supports Back-annotate Physical Constraints

constraints to Vref Constraints, as shown in Figure 4-20.
